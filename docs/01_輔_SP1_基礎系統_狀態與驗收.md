## 二、工作與交付順序

- 先完成 SP1 正式驗收，之後才開始新增 SP2；SP2 完成後才開始新增 SP3。
- SP1 獨立交付入口是 `deliverables/sp1/`。
- SP1、SP2、SP3 各自保留可追溯的獨立交付區域／檔案；到 SP3 階段另產生
  一份 SP1＋SP2＋SP3 完整整合交付。
- 既有整合分支成果保留，不回退，也不誤標成 SP1 獨立成品。

## 四、已具備的 SP1 工程基礎

- 啟動、集中路徑、JSON 設定、服務註冊、事件與紀錄
- 結構化自我檢查與損壞設定保留／重建
- Recovery、Smart Reconnect、External Adapter 穩定契約
- 唯讀 Windows 視窗列舉、缺失／重複／最小化／無效範圍拒絕
- 操作區域重疊檢查與關閉時清除快取
- 背景能力報告與唯讀 `PrintWindow` 擷取探測
- PyInstaller 規格、GitHub Actions Windows 建置、成品中繼資料與 SHA-256
- `release/latest` 只允許由 `main` push 發布，分支快照不會覆蓋正式發布
- SP1 正式包固定追蹤專用 `release/sp1`，不會前進到 SP2／SP3／完整整合版
- 單一玩家更新入口「更新輔」
- 同一提交逐檔雜湊驗證、鎖定、暫存、原子替換、安裝後驗證及失敗回復的
  交易式更新流程
- 完整首次安裝器、舊安裝備份／回復及單一執行檔圖示捷徑
- Win32 ABI、64 位元控制代碼、視窗身分保存及 GDI 資源釋放強化

## 七、最後需要外部確認的最小資料

以下資料未確認前維持停用，不自行猜測：

1. 乾淨帳號：需要一個可互動登入的新 Windows 使用者或已啟用的 Windows

2. 14 視窗身分：使用者已確認以桌面捷徑啟動參數的不可逆匿名 SHA-256

   各指紋仍屬玩家可見視窗登記語義，維持暫停；不得自行猜測。
3. 無害輸入：允許測試的確切按鍵或點擊位置、預期不會改變遊戲資料的反應，
   以及前景／非前景／最小化各自是否允許。

   的步驟、重試次數與何時交還玩家。登入權杖、捷徑參數與帳號秘密不得寫入
   倉庫、測試輸出或交接文件。
